# Features

Tablero de las 43 features. Cada carpeta contiene `spec.md`, `tasks.md` y `handoff.md`.

## Estados

`draft → ready → in-progress → review → accepted → done`

- `draft`: spec completa, pero dependencias o decisiones pendientes.
- `ready`: DoR cumplida; puede empezar.
- `in-progress`: en implementación.
- `review`: pendiente de revisión/aceptación.
- `accepted`: aceptada por el usuario.
- `done`: documentación y evidencias cerradas.

## Niveles de auditoría

El nivel de cada feature se fija en la columna `Auditoría` del tablero y decide el alcance de su revisión. Exigencias detalladas por nivel: [protocolo de revisión](../06-process/review-protocol.md).

- **A — alto riesgo:** una equivocación filtra datos de otros, permite actuar como otro usuario o expone binarios privados.
- **B — UI sobre kit:** pantalla compuesta con componentes ya auditados, sin lógica de permisos nueva.
- **C — bajo riesgo:** PWA, contenido, ajustes cosméticos y tooling.
- **V — verificación:** el producto de la feature es el informe de auditoría.

Reglas:

1. El nivel lo cambia **solo el usuario**.
2. Toda feature empieza su G1 declarando su nivel; si el agente cree que está mal asignado, lo reporta sin actuar.
